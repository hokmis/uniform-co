# 匯入、匯出與鼎新 ERP 介面規格

- 狀態：基準規格；鼎新欄位待樣本補齊
- 相關文件：[制服管理系統需求規格](./product-requirements.md)

## 1. 共通原則

1. 匯入與匯出使用版本化範本，檔案顯示範本版本與產生日期。
2. 匯入採「上傳／解析 → 預覽 → 確認發布」；預覽不改正式資料。
3. 每批保存檔名、檔案雜湊、操作者、時間、範本版本、成功／失敗列數及錯誤報告。
4. 同一檔案或同一批次重送不得重複建立庫存流水。
5. 匯出資料使用 UTF-8；若鼎新樣本要求 Big5、特定 CSV 引號、固定長度或 Excel 格式，則由版本化轉接器處理。
6. 第一版採整批套用：任一列驗證失敗時不發布任何正式資料；解析工作可以分塊，但確認發布必須可整批回滾。
7. 更新既有主檔時，匯入檔空白欄位不代表清除現值；第一版需要清除選填值時由有權角色在主檔畫面明確操作並留稽核，不用空白儲存格猜測意圖。
8. 上傳前先以冪等命令建立 `AWAITING_UPLOAD` 批次及唯一、不可覆寫的 private Storage key；只有後端確認該 key 的 MIME、實際大小、SHA-256 與完成 metadata 後，才轉 `UPLOADED` 並建立解析工作。逾期未完成批次可取消，回應遺失時查回原批次／key，不另建孤兒上傳。

### 1.1 不可信 XLSX／CSV 防護

所有上傳檔都視為不可信輸入，且在正式解析前先通過下列防線：

- 同時驗證副檔名、宣告 MIME 與檔案 signature；不因檔名是 `.xlsx` 或 `.csv` 就信任內容。
- 以可設定上限限制原始檔大小、解壓後總大小、ZIP entry 數、壓縮比、工作表數、列數、欄數、單一儲存格長度與總儲存格數；超限整批拒絕，不進入預覽。
- XLSX 拒絕加密檔、路徑穿越 entry、巨集、DDE／外部連結、嵌入物件及公式儲存格；解析器不得執行公式、巨集或發出外部網路請求，也不得信任公式快取值。
- CSV 只接受明確允許的編碼與分隔符，拒絕 NUL、欄數異常、超長列及解析後欄位漂移；錯誤報告指出列號，但不把整列敏感資料寫入平台 log。
- 工號、機構代碼、部門代碼、制服品號、供應商代碼等識別欄必須以文字型別匯入並逐字保存前導零。若 XLSX 把識別值存成數字、日期或科學記號，該列報錯，不做猜測性轉型。
- 一般 XLSX 匯出把可能以 `=`, `+`, `-`, `@`、tab 或 carriage return 開頭的使用者文字寫成明確的文字儲存格；CSV 匯出使用一致且可測試的公式注入中和規則。鼎新專用輸出不套用會改變契約的通用轉義，只能輸出版本化映射中已驗證的欄位與固定值。
- 所有正式驗證必須在受控後端再執行；瀏覽器端檢查只提供即時提示，不能成為唯一防線。

## 2. 主檔匯入

### 2.1 員工

必要欄位：工號、姓名、機構代碼、部門代碼、在職狀態。

選填欄位：職稱、到職日、離職日、備註。

- 以工號比對。
- 新工號：預覽為新增。
- 相同工號且欄位不同：預覽差異；確認後更新目前基本資料。
- 不改寫歷史交易快照。
- 檔案缺少既有員工：不刪除、不自動停用。
- 在職員工缺機構或部門：整列錯誤，不發布。

### 2.2 機構與部門

- 以穩定代碼比對，不以名稱比對。
- 部門匯入必須引用有效機構代碼。
- 已被引用的代碼不得改成另一個業務實體，也不得重用。

### 2.3 制服

- 以唯一品號比對，且該品號等同鼎新 ERP 品號。
- 相同品號更新描述資料；不得藉由更新把一個歷史品號變成不同制服。
- 品名、計量單位與啟用狀態必填；尺寸選填。

### 2.4 供應商

- 以供應商代碼比對。
- MOQ 可按「供應商＋制服品號」維護，不能只存一個全域 MOQ 後覆蓋不同廠商條件。
- 匯入 MOQ 前，供應商代碼與制服品號都必須存在；相同組合更新條件，不新增重複關係。

## 3. 期初庫存匯入

- 只允許在正式切換作業中，由系統管理員執行。
- 唯一鍵為「倉庫＋制服品號」。
- 數量必須為非負整數。
- 每一列制服品號及倉庫必須已存在且啟用。
- 預覽顯示各倉總量與錯誤列；發布使用單一批次並建立期初庫存流水。
- 正式環境以單一 `system_cutover_state` 作全域 gate：發布時鎖定 PRE_CUTOVER singleton，把唯一整批期初 posting、兩倉餘額、來源批次及狀態轉 LIVE 在同一交易完成。
- 不只同一批次不得重複發布；任何第二個期初批次、不同冪等鍵或 LIVE 後的期初發布都必須拒絕。PRE_CUTOVER 時所有非期初庫存過帳亦須拒絕。

## 4. 一般資料匯出

主檔、庫存、發放、調庫差異、換季、採購、入庫、盤點及稽核查詢皆可依目前篩選條件匯出 XLSX 或 CSV。大量匯出權限與下載行為須記錄於稽核紀錄。

## 5. 鼎新 ERP 銷貨匯出

### 5.1 資料資格

- 來源必須是倉庫已成功 `POST` 且鎖定的人資需求單。
- 只取人資發放量，不取增庫量、調庫量、採購入庫或換季需求。
- 已被正式邏輯批次涵蓋的來源明細不可再次進入另一批一般銷貨邏輯批次；後續更正與退回以各自來源建立調整批次。

### 5.2 分組與彙總

- 表頭分組鍵：發放日期（Asia/Taipei）＋機構。
- 每組對應一個正式邏輯批次及一張鼎新銷貨資料 snapshot。
- 組內依制服品號加總數量。
- 系統保留邏輯批次、表頭、品號彙總列到原人資需求單及員工發放明細的完整對照。候選來源在同一交易鎖定並建立唯一來源連結，兩個並行請求不得重複涵蓋同一發放明細。

### 5.3 批次生命週期

```text
                         ┌──────── artifact 重試／新 revision ────────┐
PREPARING ───────────→ GENERATED ─────────→ DOWNLOADED ─────────→ IMPORT_CONFIRMED
    │                       │                    │
    └→ GENERATION_FAILED ───┘                    └→ IMPORT_FAILED ──────┘
```

邏輯批次與檔案 artifact 分開管理：

- 邏輯批次在 `PREPARING` 時便凍結來源明細、日期＋機構分組與品號彙總 snapshot。來源連結以唯一約束防止同時產批；`create_erp_export_batch` 使用冪等鍵，並在 snapshot transaction 建好 batch／source links 後即回傳 SUCCEEDED 與同一 batch，不等待檔案產生。
- 邏輯批次狀態只允許 `PREPARING`、`GENERATION_FAILED`、`GENERATED`、`DOWNLOADED`、`IMPORT_FAILED`、`IMPORT_CONFIRMED`。尚未被批次占用是來源資格，不是批次狀態。
- 每個具名格式／映射產檔版本由獨立的 `request_erp_artifact` 冪等命令建立一個 PREPARING artifact revision 及第一個 PENDING attempt；request 先鎖 logical batch，重驗 `active_artifact_id` 為空且不存在其他 PREPARING artifact，再設定 active pointer。資料庫 partial unique constraint 保證每個 batch 最多一個 PREPARING revision；finalize／terminal fail 只有在 active pointer 仍指向本 artifact 時才能推進批次並清空 pointer。該命令在耐久工作建立時即 SUCCEEDED，不等待 READY。artifact 保存邏輯批次編號、revision number、格式／映射版本、檔案位置、內容 SHA-256、產生人、時間與結果。同一 revision 的暫時性 worker 重試以獨立 render attempt 留痕，不因每次技術重試就增加 revision；確認該 revision 失敗或映射改版後，才建立下一 revision。失敗 revision 保存錯誤分類及安全化訊息，不留下可下載的半成品；舊 revision 或競爭 attempt 不得成為 current 或改變 batch 狀態。
- 產檔成功後狀態為 `GENERATED`；下載後為 `DOWNLOADED`。重複下載同一 revision 必須取得完全相同的位元內容、雜湊及邏輯批次編號，每次下載另留事件紀錄。
- 產檔技術失敗時為 `GENERATION_FAILED`；鼎新拒絕檔案時為 `IMPORT_FAILED`。修正格式映射後，同一邏輯批次先回到 `PREPARING` 並建立下一 artifact revision，再依結果進入 `GENERATED` 或 `GENERATION_FAILED`；不得另建邏輯批次、釋放來源，或把格式重建誤稱為業務調整批次。所有舊 revision 永久保留且不可覆寫。
- 使用者確認鼎新已匯入時改為 `IMPORT_CONFIRMED`，可填鼎新單號或備註；取得自動回執與否待鼎新契約確認。`IMPORT_CONFIRMED` 是終態，不得再為同一業務 snapshot 產生新 artifact revision；後續業務變動只能走更正／退回調整批次。
- 真正的發放更正或退回才另建調整邏輯批次並關聯原批次；是否輸出負數、退貨單、折讓或其他單別，待鼎新樣本確認。
- 邏輯批次建立及 artifact revision request 各自使用 operation command 與冪等鍵；render attempt 則使用自身 fencing lease，不共用或延長前兩者的 command claim。若 HTTP 回應遺失，同鍵且相同 payload 的重試只回傳既有批次／revision；同鍵但 payload 不同須拒絕並記錄衝突。用戶端亦可依冪等鍵查詢結果，不得因逾時製造第二批或第二份不明檔案。

### 5.4 待提供的鼎新契約

在取得以下資料前，不宣告鼎新匯出完成：

1. 鼎新產品與版本、匯入功能名稱。
2. 一份已成功匯入的原始檔。
3. 必填表頭與明細欄位、欄位長度及允許值。
4. 檔案格式、編碼、分隔符號、日期、數字、小數與負數格式。
5. 客戶、部門、倉別、業務員、幣別、稅別、單價等固定值或對照來源。
6. 外部參考單號的長度及唯一性規則。
7. 更正、退回與重匯的鼎新處理方式。

### 5.5 驗證方式

- 以實際成功樣本建立黃金測試檔。
- 每個轉接器版本用固定測試資料比對輸出內容與編碼。
- 在鼎新測試帳套完成至少一次新增、重複匯入防護及更正／退回測試。
- 以兩個並行建立請求驗證同一來源只歸入一個邏輯批次；以回應遺失後同冪等鍵重試驗證不重複占用來源。
- 模擬產檔失敗及鼎新匯入失敗，驗證來源 snapshot 不變、舊 artifact revision 不覆寫，且重試只在同一邏輯批次追加 revision；以不同冪等鍵並行要求 artifact，驗證每批最多一個 active PREPARING，過期 revision 不得奪取 current 或推進批次。

## 6. 檔案安全

- 真實員工資料、匯入原檔與鼎新檔不得提交 GitHub。
- 下載功能依角色及資料範圍授權。
- 暫存檔設定保存期限；稽核資料與批次中繼資料依公司保存政策保留。
- 被拒絕的上傳檔不得進入正式解析工作或被其他使用者下載；若為除錯而暫存，須放在私有隔離區、設定短保存期限並限制管理權限。
- 正式 artifact revision 存於私有空間，只能透過短效授權下載；刪除政策不得讓仍在法定／公司保存期內的邏輯批次失去內容與雜湊對照。
