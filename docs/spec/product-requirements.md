# 制服管理系統需求規格

- 狀態：訪談與風險稽核基準版
- 基準日期：2026-08-12（Asia/Taipei）
- 技術邊界：GitHub、Vercel、Supabase，第一版以免費方案為前提
- 業務詞彙：[CONTEXT.md](../../CONTEXT.md)

## 1. 目的與成功標準

本系統取代制服作業使用的紙本、Excel 與 Google Sheet，建立一套可追溯的人員發放、兩倉庫存、換季需求、採購、入庫、盤點、列印及鼎新 ERP 匯出流程。

成功標準：

1. 人資登記發放時，逐筆關聯員工與制服品號，且輸入量不得超過帳面可申請量。
2. 人資倉與總倉的每筆數量變化都有來源單據、操作者及時間，不允許直接改庫存餘額。
3. 人資需求量與倉庫實際調庫量並存，差異可見但不形成待補義務。
4. 換季需求由各需求窗口在授權範圍內填報，經人資修正、執行長核准、採購 MOQ 評估、採購及入庫完成閉環。
5. 已發貨資料不可改寫；更正、退回、盤點及匯出均可追溯。
6. 可列印正式單據，並可依指定格式輸出鼎新 ERP 銷貨資料。

## 2. 組織與角色

二十家機構共用一個人資倉與一個總倉。機構與部門是員工歸屬、需求窗口權限、成本及報表維度，不是庫存地點。

第一版角色：

| 角色 | 核心責任 |
|---|---|
| 系統管理員 | 帳號、角色、權限範圍及主檔管理 |
| 人資 | 員工、人資需求、發放、增庫、補庫、人資倉與換季彙整 |
| 倉庫 | 總倉、實際調庫、發貨、採購入庫及總倉盤點 |
| 採購 | 供應商、MOQ、採購單、價格及進度 |
| 執行長 | 換季核准 |
| 需求窗口 | 授權「機構＋部門」範圍內的換季需求登記 |

同一帳號可兼任多個角色；系統仍須記錄實際登入帳號，不使用共用帳號替代稽核。

## 3. 主檔需求

### 3.1 員工主檔

必要欄位：工號、姓名、機構、部門、在職狀態。選填欄位：職稱、到職日、離職日、備註。

規則：

- 工號在二十家機構間唯一，跨機構調動不變，離職後不重用。
- 每位在職員工只有一組目前機構與部門，且不得缺漏。
- 員工基本資料不保存身分證字號、電話、地址等制服作業不需要的敏感個資。
- 發放及換季明細關聯員工，同時保存交易當時的工號、姓名、機構與部門快照。
- 員工調職、改名或停用不改寫歷史快照。
- 已被交易引用的員工只能停用，不能刪除。

### 3.2 組織主檔

- 機構的代碼、名稱、啟用狀態，以及部門的所屬機構、代碼、名稱、啟用狀態必填；機構代碼全域唯一，部門代碼在同一機構內唯一。
- 機構與部門可維護、匯入、匯出、排序及停用。
- 部門名稱不作全公司唯一識別；權限以明確的機構與部門識別碼組合判斷。
- 需求窗口可被授權一組或多組「機構＋部門」，並可跨機構、跨部門。

### 3.3 制服主檔

必要欄位：唯一品號、品名、計量單位、啟用狀態。選填欄位：尺寸、類別、季別、性別／版型、顏色、預設供應商、安全庫存量、備註；MOQ 依「供應商＋品號」選填。

規則：

- 唯一品號與鼎新 ERP 品號相同，是唯一庫存識別。
- 同款制服若有不同尺寸，每個尺寸使用不同品號；無尺寸商品可不填尺寸。
- 庫存檢查、預留、調庫、盤點及匯出均逐品號計算，不得以其他品號抵充或自動替換。
- 已被交易引用的品號只能停用，不能刪除。
- 第一版不區分可用、待驗、瑕疵或隔離庫存；系統內庫存一律視為可發放。

### 3.4 供應商主檔

供應商代碼、名稱與啟用狀態必填；統一編號、聯絡人、電話、電子郵件、地址、預設幣別、各制服品號 MOQ 與備註選填。已被採購單引用者只能停用；同一品號若有多個供應商，可分別保存不同 MOQ。

## 4. 核心庫存規則

以下公式均逐制服品號計算：

```text
調庫需求量 = 發放量 + 增庫量
可申請量 = 人資倉現有量 + 總倉現有量 - 尚未完成的預留量
調庫差異量 = 調庫需求量 - 實際調庫量
```

規則：

1. 人資輸入的「發放量＋增庫量」不得超過當下可申請量；超過上限時欄位不得接受該數量，單據亦不可送出。送單成功只使需求進入預留與待發貨，制服不得在倉庫正式 `POST` 前交付。
2. 人資需求單送出後，完整的「發放量＋增庫量」成為跨兩倉的品號合計預留量，直到取消、發生盤點衝突或倉庫正式發貨。畫面只顯示 `combined_reserved` 與 `available_to_request`，不得宣稱某筆預留已分配至特定倉庫。
3. 人資決定發放量與增庫量；倉庫不得修改，只能填實際調庫量。倉庫草稿必須保存 `source_request_row_version`；人資更正來源後，舊草稿失效，版本不一致時不得正式發貨。
4. 實際調庫量預設為「調庫需求量」與「總倉發貨當下可移出量」的較小值。倉庫可人工填得更少，但必須填寫短發原因；差異醒目標示，不建立待補量、不自動延續。
5. 倉庫 `POST` 是實際調庫、員工交付與正式帳務的共同鎖點：以單一資料庫交易完成總倉減少、人資倉增加、員工發放扣除、預留關閉、庫存流水建立及單據鎖定；任何結果不得讓倉庫庫存為負數。只有成功 `POST` 的發放才完成正式帳務並具備鼎新匯出資格。
6. 若盤點調減後的兩倉品號合計小於該品號有效預留總量，盤點仍在同一交易過帳，但受影響預留改為 `CONFLICTED`，來源需求單改為 `INVENTORY_REVIEW_REQUIRED`，且不得發貨；人資須重新檢查、調整並再次送出，通過當下庫存驗證後才能恢復處理。
7. 庫存餘額不得由畫面或匯入檔直接覆寫；所有變化來自期初、採購入庫、調庫發貨、發放、更正、退回或盤點調整。
8. 雖然通常只有一位人資操作，所有檢查與異動仍須具備原子性及冪等性。高風險交易統一依「冪等命令 → 依品號排序的共同互斥列 → 來源單／業務根列 → 依品號與倉庫排序的餘額 → 依品號與來源排序的預留」加鎖；網路逾時後以冪等鍵查回既有結果，不得盲目重建交易。

## 5. 人資發放與補庫

### 5.1 人資需求單

- 人資在交付制服前建立發放明細；每筆包含本次發放日期、員工、工號快照、姓名快照、機構快照、部門快照、制服品號、品名快照、尺寸快照及數量。
- 發放量由人資逐筆輸入，系統按品號彙總。
- 增庫量由人資按品號輸入，不關聯員工。
- 同一張需求單可包含多位員工與多個品號。
- 送出交易成功並取得單號後，需求進入預留與倉庫待發貨；送出本身尚不代表員工已領取。倉庫完成理貨及現場核對、準備立即交付時執行 `POST`，成功後才把制服交給員工並視為正式交付與扣帳；不另要求人資再按一次「完成發放」。
- 送出後「可申請量」立即扣除預留；正式兩倉現有量與庫存流水在倉庫發貨時一次過帳。畫面須同時顯示現有量、預留量與可申請量，避免把尚待倉庫發貨的數量誤認為仍可使用。
- 倉庫 `POST` 前，人資可更正，系統自動保存原值、新值、操作者與時間；備註選填。每次更正都增加來源版本並使既有倉庫草稿失效，倉庫必須重新載入最新版本。
- 發貨前只有誤建／重複單可填原因取消；依規定此時尚未交付。若發生例外的提前交付，須以更正或退回追蹤實物異動，不能用取消釋放數量。
- 若盤點使預留失效，單據進入 `INVENTORY_REVIEW_REQUIRED`，不得交由倉庫 `POST`；人資須依最新可申請量調整或重新確認。
- 倉庫成功 `POST` 後原單永久鎖定，正式發放日沿用人資送出時保存的發放日期。

### 5.2 補庫單

- 補庫單不包含員工發放明細，只申請從總倉補充人資倉。
- 補庫單送出時不建立庫存預留，也不以兩倉合計量阻擋送單；畫面可提示當下總倉量，但不是發貨承諾。
- 倉庫發貨時重新鎖定並檢查總倉餘額；實際調庫量預設為補庫需求量與發貨當下總倉可移出量的較小值，且不得超過該上限。
- 倉庫人工填寫低於預設值時必須填短發原因。差異仍醒目標示、不形成待補，完成後只依實際量減總倉、加人資倉。

### 5.3 發貨後處理

- 登記錯誤：建立關聯原單的更正單，以發放、調庫、採購入庫、盤點或退回更正類型分別處理，不修改原單；只有員工發放更正、員工退回及退回更正可能形成鼎新調整批次，實際單別與正負號待鼎新格式確認。
- 員工退回：建立退回單並必填原因；確認仍可發放後才增加人資倉庫存。
- 更換尺寸：退回原品號後，另建新發放明細。
- 第一版不追蹤不可用退回品；不可再次發放者不計入系統庫存。
- 發放更正、退回與退回更正都必須鎖定同一原發放明細，並保證「原發放量＋已過帳發放更正」不得小於零，且「原退回量＋已過帳退回更正」不得小於零或超過該有效發放量；並行操作只能有符合全部條件的交易成功。
- 所有會減少帳面庫存的更正都須在鎖後重驗。若會讓任一倉庫為負，或屬可延後的額外發放而沒有未預留可用量，整筆拒絕；若採購入庫、盤點或退回更正是在修復真實帳實錯誤，且會使兩倉合計不足以覆蓋既有預留，則真實庫存更正與受影響需求／預留的衝突狀態必須在同一交易完成。

## 6. 換季需求與採購

### 6.1 換季需求活動

- 人資建立活動名稱、季別、開放時間、截止時間、適用員工及可選品號。
- 需求窗口只能查看及登記授權「機構＋部門」範圍內的在職員工。
- 明細逐員工、逐品號登記；「活動＋工號＋品號」只能有一筆，重複操作更新同一筆。
- 截止後窗口不可修改；活動在人資彙整／執行長退回狀態時，人資可直接修改並標示異動，備註選填，系統自動保留異動紀錄。已有版本待執行長審查時，人資不得修改或另送新版，須等待核准或退回。
- 換季需求只作採購評估，不預留庫存、不代表員工已領取。

### 6.2 核准與採購順序

固定順序：

```text
窗口填報 → 人資彙整修正 → 執行長核准 → 採購評估 MOQ → 建立採購單 → 到貨驗收 → 總倉入庫
```

- 執行長核准的是人資彙整後、不可變的完整送核版本。人資送核與執行長核准／退回共鎖同一活動；每個活動最多一個待核版本，待核時人資不可修改或重送。核准／退回命令必須帶入畫面所見的送核版本 ID、revision 與內容雜湊；若目前待核版本已變，系統拒絕舊畫面操作並要求重新載入。
- 執行長也可退回人資，退回理由必填；人資修正後重新送核。退回不建立核准快照，先前提交版本與理由仍保留於稽核紀錄。
- 第一版由採購為每個核准品號選定一個供應商；可依該供應商與品號的 MOQ、包裝倍數或供貨限制調整最後採購量，不需再次送執行長核准。同一品號雖可在主檔維護多個候選供應商，本次採購決定只使用被選定者。
- 最後採購量與核准量不同時，系統標示差異並要求採購選擇原因；補充備註選填。
- 採購入庫後回到標準的人資需求／補庫流程，不直接視為員工已領取。

### 6.3 採購單與驗收

- 採購單包含供應商、單號、日期、預計到貨日、品號、數量、幣別、未稅單價、稅別、稅額、總金額及狀態。
- 系統管理採購與入庫，不管理付款、會計傳票或應付帳款。
- 同一最後採購決定可拆給多張採購單，但每列品號必須等於該採購決定引用的核准品號，不得用 A 品號的上限採購或入庫 B 品號；所有有效採購明細配置量合計不得超過目前採購上限。開放中的採購明細以訂購量計，`CANCELLED` 計 0，`CLOSED_SHORT` 以更正後累計合格入庫量計；若確須調高合計上限，採購先建立具理由且可追溯的採購決定調整，不得只放大採購單數量。
- 尚無任何已確認入庫紀錄的採購單才可填必填理由取消；只要已有正式收貨，即使全部拒收、合格量為零，不再收貨時也須以 `CLOSED_SHORT` 填必填理由結清，不得取消或偽裝成全數到貨。
- 允許分批到貨及短收；未到量保留在採購單，直到全數入庫、取消或短收結清。
- 損壞或不合格品不計入庫存。
- 超收時先禁止入庫；採購調整採購量並填原因後才能驗收入庫。
- 每張入庫明細的到貨量必須大於零，且合格量加拒收量必須恰等於到貨量；合格實收量只增加總倉。
- 入庫 `POST`、採購數量／上限調整、採購單取消與短收結案必須依共同順序鎖定同一採購單、採購決定及相關採購明細，鎖後重驗單據狀態、正式收貨是否存在、有效合格累計與配置量；並行操作不得造成終止後入庫、超收、超出目前採購上限，或把訂購量降到既有有效入庫量以下。
- 採購入庫更正須在同一鎖定交易重算有效到貨、合格、拒收、未完成量、採購配置量及狀態。更正使已完成採購單重新不足時轉為 `REOPENED` 並記錄原因為入庫更正；原本已 `CLOSED_SHORT` 者仍保持不可再收貨的終態，但以更正後有效數量更新進度與配置量。
- 已 `RECEIVED` 的採購單若具理由調高訂購量，必須在同一交易轉為 `REOPENED`、重算目前採購上限內的配置與未完成量；不得同時顯示已完成及仍有待收。`CLOSED_SHORT`／`CANCELLED` 不得再改訂購量，追加需求另開採購單。

## 7. 盤點與庫存調整

- 人資盤點人資倉，倉庫人員盤點總倉。
- 盤點單保存帳面量、帳面餘額版本、實盤時間、實盤量、差異量與原因。
- 確認盤點時若餘額版本已變，單據改為 `STALE_COUNT` 且不得過帳；使用者必須重新實盤，不可只把舊實盤量套到新帳面量。
- 版本一致時才建立庫存調整流水，不直接覆寫原餘額；若調減使兩倉合計低於有效預留，須同交易執行第 4 節的預留衝突處理。
- 已確認盤點單不可改寫；錯誤以關聯更正處理。

## 8. 列印、匯入與匯出

- 人資需求／發放、補庫／倉庫發貨、換季彙總／核准、採購、採購入庫、盤點、更正及退回單皆可輸出 A4 PDF。
- 正式列印版包含單號、狀態、日期、操作者與簽名欄；草稿帶明顯浮水印。正式 PDF 只能從已鎖定來源產生，每次產生明確保存來源 snapshot 版本與來源 hash、範本版本、成品內容雜湊及不可變 artifact revision；因版型或技術問題重產時建立下一 revision，不覆寫舊檔。
- 匯入支援預覽、新增／更新／錯誤分類及逐列錯誤報告。
- XLSX／CSV 匯入在解析與預覽階段防範偽造檔案類型、巨型壓縮檔、巨量列欄／儲存格、巨集、外部連結與公式；任何公式都不得在伺服器或瀏覽器執行。工號、機構／部門代碼及品號一律按文字保留前導零，不得自動轉科學記號。
- 一般 XLSX／CSV 匯出須防止試算表公式注入；鼎新檔則只由版本化欄位映射輸出已驗證值，不可用通用轉義任意改變鼎新契約。
- 歷史主檔透過停用保留，不因匯入缺少一列而刪除。
- 鼎新 ERP 銷貨匯出詳見 [import-export.md](./import-export.md)。

## 9. 查詢與報表

第一版至少提供：

- 各倉各品號現有量、品號跨兩倉合計預留量、可申請量及安全庫存提示；不得把跨倉預留顯示成任一倉的已占用量。
- 員工完整領用歷程與當時機構／部門快照。
- 依日期、機構、部門、員工、品號、尺寸的發放統計。
- 調庫需求、實際調庫及差異統計。
- 換季填報進度、核准量、原最後採購量、目前採購上限與採購差異／調整原因。
- 採購未到量、到貨與入庫進度。
- 盤點差異、更正、退回、匯入批次與稽核紀錄。
- 尚未匯出及已匯出鼎新的發放資料。

## 10. 非功能需求

- 繁體中文介面；時間以 UTC 儲存、Asia/Taipei 顯示及分組。
- 第一版僅支援連線作業，不提供離線新增或同步。
- 每位作業者使用個人帳號；角色及範圍權限在資料庫層強制執行。
- 重要寫入使用資料庫交易、固定加鎖順序、冪等鍵及回應遺失後的結果查回機制，不依賴前端檢查維持庫存正確。
- 正式、測試與預覽環境隔離；預覽部署不得寫入正式資料。
- 匯入原檔、正式匯出批次及重要異動具操作者、時間與來源追蹤。
- 在免費方案限制內採用配額監控、資料庫與私有檔案的可還原異地備份、定期隔離環境還原演練及明確升級門檻；實際限制以官方查核文件為準。

## 11. 上線資料切換

- 設定正式上線日。
- 匯入機構、部門、員工、制服、供應商主檔及兩倉期初庫存。
- 正式環境只有一個全域切換鎖：期初庫存整批發布、唯一 opening posting、兩倉餘額及 PRE_CUTOVER → LIVE 必須同交易完成；LIVE 前不得做一般庫存過帳，LIVE 後任何第二次期初發布都拒絕。
- 舊紙本、Excel、Google Sheet 交易只封存，不轉成新系統交易。
- 上線前完成兩倉實盤，期初匯入總數須與簽核的盤點結果一致。

## 12. 明確不在第一版範圍

- 離線操作。
- 每位員工自行登入填寫換季需求。
- 不可用、隔離、報廢庫存的在庫狀態管理。
- 付款、會計傳票、應付帳款。
- 舊交易明細搬遷。
- 未取得格式前的鼎新 API 或雙向同步。
