# 制服管理系統：工作流程與權限規格

## 1. 文件目的與適用範圍

本文件依需求訪談的已確認決策，定義制服管理系統的業務流程、單據狀態、角色權限、庫存控制、稽核與列印規則。業務名詞以根目錄的 `CONTEXT.md` 為準；本文件不另行改變其定義。

系統使用一個人資倉及一個總倉，供二十家機構共同使用。機構與部門是員工歸屬、需求、成本與報表的分類，不是庫存位置。所有庫存只以唯一制服品號分開計算；制服品號同時是鼎新 ERP 品號，同款不同尺寸必須使用不同品號。

本版採純線上作業，不提供離線新增、暫存或同步。

## 2. 全流程共同規則

1. 所有數量檢查均逐一依制服品號進行，不得用其他品號或尺寸抵充。
2. 庫存不得為負數；任何送單、發貨、入庫、盤點確認、更正或退回確認，都必須在伺服器端再次檢查並以不可分割的交易完成。
3. 庫存餘額不得直接編輯，只能由期初庫存、倉庫發貨、採購入庫、盤點確認、更正或退回等正式紀錄產生異動。
4. 送出的人資需求單會占用品號跨兩倉的合計預留量，避免同一庫存被其他人資需求重複使用。取消時釋放預留；倉庫 `POST` 時，預留轉為正式庫存異動。單獨補庫單不建立預留。
5. 已被交易引用的員工、機構、部門、制服品號、供應商及倉庫資料不得刪除，只能停用；未被使用的誤建資料才可由有權限者刪除。
6. 同一帳號可具備多個業務角色，但每次操作均記錄實際登入帳號，不使用共用帳號取代操作者身分。
7. 本系統不設不可用庫存。採購驗收不合格品不入庫；員工退回品須確認可用後才入庫。
8. 日常人資作業不增加「待發放」、「部分發放」等人工確認按鈕；人資只需一次登錄及送出。送出成功後單據進入倉庫待發貨，但制服不得在倉庫 `POST` 前交付；倉庫一次填寫實際調庫量並 `POST`，該動作同時是本次調庫、員工交付、帳務完成及原單永久鎖定的正式界線。
9. 預留只以 `combined_reserved` 表示品號跨兩倉合計占用，`available_to_request = combined_on_hand - combined_reserved`；不得顯示或承諾某筆預留來自人資倉或總倉。
10. 盤點調減若使 `combined_on_hand` 小於同品號有效預留總量，盤點與衝突標記須同交易完成：受影響預留改為 `CONFLICTED`，來源人資需求單改為 `INVENTORY_REVIEW_REQUIRED`，在重新驗證成功前不得發貨。
11. 所有高風險庫存交易統一依「冪等命令 → 依 item_id 排序的共同互斥列 → 來源單與業務根列 → 依 item_id、warehouse_id 排序的餘額 → 依 item_id、來源排序的預留」取得鎖；採購入庫及訂購量／採購上限調整共同鎖定採購決定與採購明細，退回及發放更正共同鎖定原發放明細。
12. 送出、發貨、入庫、盤點、更正、退回及 ERP 批次建立都使用冪等鍵。用戶端若遺失回應，須先以冪等鍵查回結果；同鍵且相同 payload 的重試回傳既有結果，不得重複建立單據或庫存流水；同鍵但不同 payload 必須拒絕並記錄衝突。

## 3. 角色、範圍與權限

### 3.1 角色定義

| 角色 | 可執行的主要作業 | 明確限制 |
| --- | --- | --- |
| 系統管理員 | 帳號、角色指派及各類主檔維護；停用或刪除尚未被引用的誤建主檔 | 系統管理員角色本身不取代人資、倉庫、採購或執行長的業務角色；正式庫存不得直接改值 |
| 人資 | 員工主檔與 Excel 匯入、日常人資需求單、補庫單、人資倉盤點、換季活動設定與彙整修正、員工發放相關更正與退回 | 不得填寫或覆寫倉庫的實際調庫量；倉庫發貨後不得修改原單 |
| 倉庫 | 查看已送出的調庫需求、填寫實際調庫量、完成倉庫發貨、採購驗收入庫、總倉盤點 | 不得修改人資填寫的發放量或增庫量；不得以待補量結案或直接修改庫存 |
| 採購 | 供應商與最低採購量資料、換季核准後的最後採購量、採購差異原因、採購單、取消、短收結清與到貨進度 | 不得改寫執行長已核准的換季核准量；最後採購量或訂購上限有差異時不得略過原因 |
| 執行長 | 查看人資彙整後的換季需求，核准換季核准量，或填寫理由退回人資 | 核准發生在採購評估最低採購量之前；採購依最低採購量調整後不再要求二次核准 |
| 需求窗口 | 在開放期間，替授權範圍內的員工登記及修改換季需求明細 | 只能處理被授權的「機構＋部門」組合；截止後不可修改；不得操作日常發放、庫存、採購或核准 |

未列於上表的寫入操作，不因使用者可查看資料而自動取得權限。

### 3.2 需求窗口的資料範圍

1. 管理員可為同一需求窗口指定一組或多組「機構＋部門」組合，並允許跨機構、跨部門設定。
2. 需求窗口只能查找及登記目前歸屬落在授權組合內的員工。
3. 每位在職員工必須且只能有一個目前機構與一個目前部門；員工調動只更新目前歸屬，不改寫歷史快照。
4. 權限重疊不會造成重複需求：同一換季需求活動、同一工號及同一制服品號只能有一筆明細。

### 3.3 關鍵欄位的修改權

| 資料 | 建立／修改角色 | 何時鎖定 |
| --- | --- | --- |
| 發放量、增庫量及員工發放明細 | 人資 | 倉庫 `POST` 後永久鎖定原單；`POST` 前的每次更正使既有倉庫草稿版本失效 |
| 實際調庫量 | 倉庫 | 倉庫 `POST` 後鎖定；草稿必須引用最新來源版本 |
| 換季需求明細 | 需求窗口；截止後僅人資可直接修正 | 執行長核准後，核准版本不得被覆寫 |
| 換季核准量 | 執行長核准；執行長亦可填理由退回 | 核准後保留為不可覆寫的核准依據；退回不建立核准快照 |
| 最後採購量 | 採購 | 採購單正式下單後由後續單據追蹤，不回寫核准量 |
| 採購入庫量 | 倉庫 | 入庫 `POST` 後鎖定該入庫紀錄 |
| 盤點差異 | 人資限人資倉；倉庫限總倉 | 版本一致並 `POST` 後鎖定；版本過期改為 `STALE_COUNT` |

## 4. 日常人資發放與調庫流程

### 4.1 數量定義與驗證

對每個制服品號，以以下符號表示本次單據數量：

- `F`：發放量，由人資逐員工填寫的發放明細加總。
- `I`：增庫量，由人資填寫，不關聯員工。
- `R`：調庫需求量，系統計算，`R = F + I`，不得人工修改。
- `T`：實際調庫量，由倉庫依總倉現有庫存填寫。
- `D`：調庫差異量，系統計算，`D = R - T`。

人資輸入數量時，系統依該品號的人資倉與總倉合計帳面可用量顯示可申請上限。送出時必須重新檢查：

`F + I ≤ 人資倉現有量 + 總倉現有量 - 其他有效預留量`

預留只在品號合計層扣除，不分攤成兩個倉庫的「各倉可用量」。任一品號超過上限，整張單不得送出；系統不得自動把需求量改小，也不得允許負庫存。

### 4.2 人資建立及送出

1. 人資建立人資需求單，填寫發放日期及逐筆員工發放明細。每筆明細關聯員工與制服品號，並保存當時的機構、部門、工號、姓名、品名、尺寸、數量等快照；尺寸若未維護於制服主檔，仍以品號作為庫存識別。
2. 新進員工尚未存在時，人資可在登記發放明細時新增員工主檔；在職員工的工號、姓名、機構、部門及在職狀態不得缺漏。
3. 人資可另外依品號填寫增庫量。系統即時計算發放量、調庫需求量及可申請量。
4. 人資送出後，系統以 `R` 建立預留，並把同一單據交由倉庫處理調庫。只有送出交易成功、回傳單號與目前來源版本後才進入待發貨，但此時仍不得先交付制服。可申請量立即下降，正式兩倉現有量與流水等到倉庫 `POST` 才一次過帳；待發貨清單必須清楚顯示這段時間差。
5. 倉庫 `POST` 前，人資可更正；每次更正增加來源 `row_version`、重算預留並自動使引用舊版本的倉庫草稿失效。誤建或重複建立的單據可在 `POST` 前填寫原因後取消並釋放全部預留。依規定 `POST` 前不得交付；若發生例外的提前交付，必須用更正或退回追蹤，不得以取消掩蓋實物異動。
6. 盤點造成預留衝突時，需求單改為 `INVENTORY_REVIEW_REQUIRED`。人資必須依最新可申請量減量或重新確認；重新送出成功後建立新的有效預留與版本，倉庫才可建立新草稿。

### 4.3 倉庫填寫實際調庫量及發貨

1. 倉庫查看人資填寫的 `F`、`I` 及系統計算的 `R`，只能填寫 `T`。倉庫草稿保存 `source_request_row_version`；顯示版本過期時只能重新載入，不得沿用舊數量。
2. `T` 的預設值為 `min(R, 總倉發貨當下可移出量)`，且不得超過這兩者；完成後也不得使人資倉帳面數量為負。倉庫人工填寫低於預設值時，`short_ship_reason` 必填。
3. 若總倉不足以完整補足 `R`，系統以現有量形成預設 `T` 並醒目標示 `D`，但不建立待補量、不自動延續至下一張單，也不要求分批發貨。日後仍需補充時，由人資另開補庫單。
4. `POST` 時須重驗來源版本一致、來源狀態不是 `INVENTORY_REVIEW_REQUIRED`、預留仍有效，以及最新兩倉餘額。任一不符則整筆失敗，不得留下部分流水。
5. 倉庫完成本次理貨、實際調庫量及領取人現場核對，準備立即交付時按一次「完成發貨」；只有 `POST` 成功後才把制服交給員工。同一交易完成以下庫存效果：
   - 總倉減少 `T`；
   - 人資倉增加 `T`，並扣除員工發放量 `F`；
   - 釋放本單預留；
   - 固定 `D = R - T`，並完成員工發放歷程。
6. 若發貨前人資倉數量為 `H0`、總倉數量為 `M0`，則發貨後為：
   - `總倉 = M0 - T`
   - `人資倉 = H0 + T - F`
7. 倉庫成功 `POST` 即形成實際交付與帳務的業務鎖點。原人資需求單、發放明細、發放量、增庫量與實際調庫量均不得再修改或刪除；只有此時才完成正式發放並取得鼎新匯出資格。

### 4.4 單獨補庫單

補庫單不關聯員工，只有人資填寫的補庫數量。送出補庫單不建立預留，也不以兩倉合計量擋單。倉庫 `POST` 時重新鎖定總倉餘額，實際調庫量預設為 `min(補庫需求量, 總倉當下可移出量)` 且不得超過此值；人工填得更少時短發原因必填。差異只標示、不形成待補，完成發貨後等量減少總倉並增加人資倉。

## 5. 換季需求、核准與採購銜接

1. 人資建立換季需求活動，設定活動名稱、季別、開放時間、截止時間、適用員工範圍及可選制服品號；活動開放時凍結適用員工的機構與部門快照，員工中途調動不改變本活動窗口歸屬。
2. 開放期間，需求窗口逐筆替授權範圍內的員工填寫制服品號及需求量。系統以「活動＋工號＋制服品號」防止重複；再次操作是更新同一筆，不重複加總，並保存修改者與修改時間。
3. 到達截止時間後，需求窗口不能再修改。活動在人資彙整或執行長退回狀態時，人資可直接修正明細；系統自動標示該筆已由人資修改並保存原值、新值、修改人及時間，備註選填，不增加退回窗口或重新提交層級。已有 PENDING 送核版本時，人資明細與重送功能鎖定。
4. 人資完成彙整後，以不可變 revision 把完整換季品號彙總送執行長核准。送核與執行長 review 共鎖同一活動；送核須鎖後確認活動仍為 HR_REVIEW、沒有 approval 或 PENDING 版本，再原子建立下一 revision 並轉 PENDING_APPROVAL。執行長可核准，或填寫必填理由退回人資；核准／退回命令必須帶入畫面所見的 submission ID、revision 與內容雜湊，鎖後若已不是目前待核版本即拒絕並要求重新載入。退回不建立核准快照，活動回 HR_REVIEW，人資修正後另建 revision 重新送核；所有提交版本與退回理由保留。核准後不得再產生新送核版本。
5. 執行長核准的數量保存為不可變的換季核准量。採購在核准之後才依供應商最低採購量、包裝倍數或供貨限制等因素決定最後採購量。
6. 最後採購量與換季核准量不同時，系統必須標示差異，且採購必須選擇差異原因；補充備註選填。此差異不需再次送執行長核准，也不得覆寫原換季核准量。
7. 第一版每個核准品號由採購選定一個供應商；同一採購決定可拆成該供應商的多張採購單，但採購明細品號必須與該決定的核准品號相同，不能借用品號 A 的上限採購品號 B。所有有效採購明細配置量合計不得超過目前採購上限；開放／完成明細以訂購量計，`CANCELLED` 計 0，`CLOSED_SHORT` 以累計合格入庫量計。若需要提高合計上限，採購須先建立具理由的採購決定調整，再增加採購單數量。
8. 換季需求量、換季核准量及最後採購量都不是員工已領取數量。採購入總倉後，仍由人資依日常流程填寫員工發放量與增庫量。

## 6. 採購與驗收入庫

### 6.1 採購單

1. 採購依最後採購量建立採購單，記錄供應商、採購單號、日期、制服品號、數量、預計到貨日及採購進度。
2. 採購單保存幣別、未稅單價、稅別、稅額與總金額，供採購單列印、供應商核對及成本統計。
3. 系統不處理付款、會計傳票或應付帳款；這些仍屬鼎新或既有財務流程。
4. 尚無任何已確認入庫紀錄的採購單才可由採購填必填理由取消。只要已有正式收貨，即使全部拒收而合格量為零，決定不再收貨時也須填必填理由改為 `CLOSED_SHORT`，保留原訂購、有效到貨／合格／拒收及未完成量；不得取消或標成全數到貨。
5. 取消、短收結案、入庫 `POST`、採購數量及採購上限調整共用同一固定鎖序；鎖定採購單、採購決定與相關明細後重新檢查狀態及正式收貨，避免取消／結案與到貨並行時兩者都依舊畫面成功。

### 6.2 分批到貨與驗收

1. 倉庫可依同一採購單建立一次或多次採購入庫紀錄。
2. 每張入庫明細的到貨量必須大於零，且合格量加拒收量必須恰等於到貨量；確認入庫時只把合格量增加到總倉。
3. 短收或分批到貨時，未到數量保留於採購單，採購單維持部分到貨狀態。
4. 損壞或不合格品記錄為驗收差異，但不增加任何庫存；系統不另設不可用庫存。
5. 超收數量不得直接入庫。採購須先在目前採購上限允許範圍內調整訂購量並填原因；需要超過目前採購上限時須先建立採購決定調整，之後倉庫才能在新上限內確認入庫。
6. 入庫 `POST` 與採購數量調整都鎖定同一採購明細並重算已入庫合格累計；新訂購量不得小於已入庫量，所有並行入庫的合格量總和不得超過當下訂購量。
7. 每筆已確認的入庫紀錄都必須保留採購單關聯及操作者，不得回頭改寫；錯誤以對應的採購入庫更正紀錄處理。更正 `POST` 時在同一鎖定交易重算有效到貨、合格、拒收、未完成量、採購配置量及狀態：已完成單重新不足時轉為 `REOPENED` 並記錄原因為入庫更正；原已 `CLOSED_SHORT` 者仍維持不可再收貨的終態，但所有進度與配置改採更正後有效數量。
8. 已 `RECEIVED` 的採購單若具理由調高訂購量，數量、配置、未完成量及 `REOPENED`（原因為訂購量增加）狀態須同交易更新；`CLOSED_SHORT`／`CANCELLED` 不得重開或改量，後續需求另建採購單。

## 7. 盤點、更正、退回與換尺寸

### 7.1 盤點

1. 人資只盤點人資倉，倉庫只盤點總倉。
2. 盤點單逐品號保存帳面量、`balance_version_snapshot`、`counted_at`、實盤量、差異量及差異原因。
3. 草稿盤點不改變庫存。確認時若目前餘額版本不同於快照，單據改為 `STALE_COUNT`，不產生流水；使用者必須重新實盤，不得把舊實盤量直接套到新帳面量。
4. 版本一致時，系統依差異產生正式庫存調整並鎖定盤點單。若調減後兩倉合計小於同品號有效預留，調整流水、預留 `CONFLICTED` 與來源需求 `INVENTORY_REVIEW_REQUIRED` 必須在同一交易完成。
5. 不得以直接覆寫庫存餘額取代盤點單。

### 7.2 發貨前更正與發貨後更正

1. 倉庫 `POST` 前，人資可在原單更正，系統自動記錄異動、增加來源版本並重新驗證、調整預留；引用舊來源版本的倉庫草稿立即失效。
2. 倉庫發貨後，原單永久鎖定。登記錯誤須建立關聯原單的更正單，以差額調整相關紀錄與庫存，並保存更正原因。
3. 更正單不得覆寫或刪除原始發放、調庫、入庫或庫存異動；所有會減少帳面庫存的更正都須在鎖後重驗。會讓任一倉庫為負，或屬可延後的額外發放而沒有未預留可用量時整筆拒絕；採購入庫、盤點或退回更正若是在修復真實帳實錯誤，且會使兩倉合計不足以覆蓋既有預留，則真實庫存流水與受影響需求／預留的衝突狀態須在同一交易完成。
4. 更正種類分為員工發放、倉庫調庫、採購入庫、盤點及退回；每種更正只關聯並修正對應來源明細。調庫更正對總倉與人資倉建立等量反向流水，不改員工發放量；採購入庫更正只調總倉；盤點更正只調原盤點倉；退回更正只調人資倉及有效退回量。員工發放更正、員工退回及退回更正可進入鼎新銷貨調整候選，其他更正不得進入銷貨匯出；實際單別與正負號待鼎新格式確認。
5. 建立及確認更正的人員須具備原業務所屬角色：員工發放與退回屬人資、倉庫調庫及採購入庫屬倉庫、盤點依倉庫歸屬由人資或倉庫處理、採購數量屬採購。
6. 發放更正、退回及退回更正須鎖定同一原發放明細，計算 `effective_issued = 原發放量 + 已過帳發放更正` 與 `effective_returned = 原退回量 + 已過帳退回更正`；兩者不得小於零，且 `effective_returned` 不得超過 `effective_issued`。三類操作任意並行時，只有鎖後仍符合全部條件者可成功。

### 7.3 員工退回與換尺寸

1. 員工退回制服時，人資建立關聯原發放單的退回單並填寫必填原因。
2. 退回品確認可用後才增加人資倉庫存；本版不保存不可用庫存。
3. 換尺寸不得直接改寫原品號：先以退回單處理原品號，再以新的發放明細處理新品號。
4. 退回 `POST` 與退回更正都鎖定原發放明細；同一明細的 `effective_returned` 不得為負或超過 `effective_issued`。與發放更正、退回更正或另一退回並行時，不符合條件者整筆失敗。
5. 已確認的退回單鎖定；錯誤仍以退回更正紀錄追溯，不無痕修改。

## 8. 單據狀態與狀態效果

狀態名稱用於表達已確認的業務界線，不增加額外人工簽核層級。

| 單據／活動 | 狀態 | 允許操作與效果 |
| --- | --- | --- |
| 人資需求單、補庫單 | 草稿 | 人資可編輯；不占用庫存，也不得據此交付制服 |
| 人資需求單 | 已送出 | 已建立跨兩倉合計預留並進入待發貨，但尚不得交付；人資可在倉庫 `POST` 前更正；誤建／重複單可填原因後取消；倉庫草稿須引用目前來源版本 |
| 人資需求單 | `INVENTORY_REVIEW_REQUIRED` | 盤點已使有效預留衝突；不得發貨，須由人資以最新庫存重新驗證、調整並送出 |

## 9. 稽核與歷史完整性

1. 系統自動保存重要欄位的原值、新值、操作者、時間及所屬單據；使用者不需為一般修改額外填寫理由。
2. 人資修正換季需求時，備註選填，但畫面必須標示已修改，且背景異動紀錄不可省略。
3. 以下操作必須填寫原因：實際調庫量人工低於系統預設值、執行長退回人資、採購量因最低採購量等因素與核准量不同、提高採購決定上限、為接受超收而調整採購量、採購單取消、短收結清、盤點差異、各類更正單及退回單。退回單另須保留原發放單關聯。
4. 員工主檔更新不得改寫歷史發放及換季需求中的工號、姓名、機構、部門等快照；同一工號仍關聯同一員工歷程。
5. 正式單據、正式 PDF artifact revision 及 ERP artifact revision 不可被新版本覆寫。版型或檔案技術問題重產時追加 revision；業務更正與退回另建關聯單據及 ERP 調整批次。
6. 初始上線只匯入主檔及兩倉期初庫存；舊紙本、Excel 與 Google Sheet 交易明細保留為外部封存，不回建成新系統交易。

## 10. 列印

以下單據均須可輸出 A4 PDF：

- 人資需求單及員工發放明細；
- 補庫單／倉庫發貨單；
- 換季需求彙總及執行長核准單；
- 採購單及採購入庫單；
- 盤點單；
- 更正單及退回單。

正式列印版須顯示單號、狀態、日期、操作者及簽名欄。未完成的草稿仍可預覽或列印，但必須有清楚的「草稿」浮水印，不得與正式版混淆。正式 PDF 只能由已鎖定來源產生，並保存來源 snapshot 版本與來源 hash、範本版本、revision、成品內容雜湊、產生人與時間；重產建立下一個不可變 revision，舊檔仍可稽核。列印不改變單據狀態。

## 11. 鼎新 ERP 銷貨匯出銜接

### 11.1 已確認規則

1. 只有倉庫已發貨、原單已鎖定的人資發放量可進入正式銷貨匯出；增庫量、調庫量、採購入庫量及換季預估需求不得匯出為銷貨量。
2. 正式邏輯批次依「發放日期＋機構」分組，每組形成一張鼎新銷貨資料，組內再依制服品號加總數量。邏輯批次凍結來源明細與彙總 snapshot，但不把某個實體檔案視為批次本身。
3. 每筆員工發放明細只能歸入一個正式邏輯批次，並須保留批次、來源人資需求單及員工明細的追溯關係。並行建立批次時必須鎖定候選來源並以唯一約束確保不重複歸批。
4. 邏輯批次狀態為 `PREPARING`、`GENERATION_FAILED`、`GENERATED`、`DOWNLOADED`、`IMPORT_FAILED`、`IMPORT_CONFIRMED`；「尚未匯出」只是尚未被任何邏輯批次占用的來源資格，不是批次狀態。
5. 每個具名格式／映射產檔版本建立不可變 artifact revision，保存 revision、格式版本、內容雜湊、檔案位置、產生人及時間；同一 revision 的暫時性技術重試另以 attempt 留痕。`PREPARING` 成功後進入 `GENERATED`；attempt 用盡或不可重試時才進入 `GENERATION_FAILED` 並保留錯誤，不得遺失或釋放已凍結的來源 snapshot。
6. 同一 artifact revision 可重複下載且位元內容與雜湊必須相同。若檔案生成失敗或鼎新因格式問題匯入失敗，修正轉接器後讓同一邏輯批次回到 `PREPARING` 並建立下一個 artifact revision；若只是重送原 READY revision 後取得成功回執，可由 `IMPORT_FAILED` 直接受控轉 `IMPORT_CONFIRMED`。所有舊 revision 永久保留，不重建邏輯批次、不再次占用來源，也不稱為調整批次。
7. `IMPORT_CONFIRMED` 是終態。真正的發放更正或員工退回才建立新的 ERP 調整邏輯批次，關聯原批次但不改寫原批次的來源 snapshot；實際正負號或鼎新單別待格式確認。
8. 建立邏輯批次與產生 artifact 都使用冪等鍵。若用戶端遺失回應，先查回既有批次／revision；同鍵重試只回傳既有結果，不得再建一批或一份內容相同但無法追溯的新檔。

### 11.2 後續依賴：待提供鼎新格式後才能定案

下列項目刻意不在本規格中推測，必須等使用者提供鼎新 ERP 銷貨單範本、檔案格式及欄位定義後補充：

- 檔案類型、編碼、分隔符號、工作表名稱及檔名規則；
- 表頭／明細欄位名稱、欄位順序、長度、必填值、固定值與日期／數字格式；
- 機構對應的客戶代號、部門／成本中心、倉別、單別、稅別、幣別等代碼映射；
- 鼎新單號與系統銷貨匯出批次編號的保存方式；
- 更正與退回調整批次使用正負數、折讓或其他鼎新單據類型的規則；
- 如何取得或登記「已確認匯入」結果，以及匯入錯誤回報欄位。

這些後續依賴不影響核心發放、調庫與庫存帳建立，但在正式驗收鼎新匯出功能前必須完成。
